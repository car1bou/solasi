# Mac 마이크 시작·긴 요약 재검증

2026-10-16 KST. 마이크 시작의 무한 대기와 잘못된 권한 안내를 수정했다. 긴 요약은 입력·문맥 전달과 지연을 보완했다. **현재 Qwen3.5:4b의 재서술은 주어·사건 성격을 안정적으로 보존하지 못해, 사용자 승인에 따라 새 로컬 일반 요약은 핵심 원문 발췌를 기본으로 적용한다.** 수치와 코드 해시는 [정제한 실행 기록](mac-microphone-summary-validation.json)에 보존한다.

## 마이크 시작

진단 앱에서 신뢰한 클릭 이후 권한 콜백이 25.784초 늦게 도착했다. macOS 마이크 권한은 이미 허용됐고 출처·메인 프레임 검사도 통과했지만, 앱의 5초 클릭 유효 기간을 넘어 거절됐다. 숨김 페이지에서 요청이 대기한 기록과 연결되며, 새로 활성화한 화면의 요청은 즉시 허용됐다. 이 기록이 모든 최초 시작 오류의 원인이라는 뜻은 아니다.

[WebKit의 getUserMedia 구현](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/mediastream/MediaDevices.cpp)에는 조건에 따라 문서가 보일 때까지 기다리는 경로가 있다. 앱에서 관찰한 지연과 일치하는 원인 후보이며, 설치된 OS의 내부 실행 경로를 직접 추적한 것은 아니다.

수정은 `frontend/src/recording-capture.ts`에 한정했다.

- 숨김 페이지에서는 `getUserMedia`를 호출하지 않고 앱 창을 앞으로 연 뒤 다시 시작하도록 안내한다.
- 연결 준비가 30초를 넘으면 시작 시도를 종료한다. 정상적인 무음은 계속 저장한다.
- 취소·시간 초과 후 도착한 스트림은 즉시 해제해 뒤늦게 녹음이 시작되지 않게 한다.
- `NotAllowedError`를 macOS 권한 부재로 단정하지 않고 연결 거절과 재시도 방법을 안내한다.
- 네이티브의 출처·메인 프레임·마이크 종류·최근 클릭 검사를 유지한다.

설치된 Solasi 앱에서 실행 후 첫 시작으로 실제 마이크 수집을 확인했다. 48kHz 모노 **134.613333초**, 원본·저장·WAV 헤더 **6,461,440프레임 일치**, `gaps=[]`, 오류 없음, 정상 종료였다. 종료 클릭의 UI 자동 승인 검토가 90초 시간 초과돼 재시도했으므로 이 길이를 앱의 종료 지연으로 해석하지 않는다. 녹음 종료 후 전사 작업도 완료됐으며 기존 페이지 필기 데이터의 해시가 같았다. 조용한 실제 방 입력의 저장 검증이고 발화 정확도 시험은 아니다.

별도로 앱 코드를 보관한 문서 폴더의 macOS 접근 요청 때문에 서버 시작이 대기했다. 사용자가 해당 요청을 허용한 뒤 실제 앱 서버가 시작됐다. 마이크 권한과 구분한 문제이며 TCC 초기화나 전체 디스크 접근 변경은 하지 않았다.

## 긴 요약 입력·검사 보완

- 새 일반 요약의 모델 입력에서 반복 시각·빈 페이지 메타데이터를 제외한다. 서버의 원본·시각·인용 연결은 보존한다.
- 같은 자료 종류는 한 번 표시하고 웹 출처의 URL·검색 시각은 유지한다.
- 일반 요약은 고정 120초 분할 대신 실제 입력 예산으로 묶는다. 회의록의 기존 분할 경계는 유지한다.
- 같은 기록에서 연속된 앞 30초 이내, 최대 320자의 전체 출처를 해석 문맥으로 전달한다. 현재 구간의 인용 enum에는 이 ID를 넣지 않는다.
- 계획과 실제 호출은 같은 입력 예산 함수를 사용한다. 첫 현재 출처도 들어가지 않을 때만 오래된 선택 문맥부터 줄인다. 문맥을 버려 본문을 더 밀어 넣지는 않는다.
- `뿐만 아니라`를 실제 부정으로 오인하는 좁은 문제를 수정했다. 실제 부정을 이 표현으로 가리는 경우도 검사한다.
- 확인 발췌의 제목에 검증되지 않은 AI의 ‘가정·조건’ 분류가 남는 경로를 수정했다. 원문에 명확한 전제가 있는 경우만 가정·조건 발췌 제목을 유지한다.
- 기존 작업의 입력 형식·구간 캐시와 엄격한 주어 직접 출처 검증을 유지한다.

## 같은 실제 음성 비교

[기존 긴 파일 검증](mac-long-file-validation.md)과 같은 LibriVox 『술 권하는 사회』 Part1, Jessie Yun의 878.303492초 낭독을 사용했다. 원본 SHA256은 `68f07d5ca8677317590af0fc1dd5b8634ae0749ba1bbddc3965962f73086f1fc`다. 두 번의 새 전체 전사에서도 확정 전사 301개·5,083문자가 이전과 문자열까지 같았다. 전체 ASR 구간 33개가 완료됐고 원본 프레임 처리 범위는 연속적이었다. 이것은 모든 단어가 정확하다는 판정이 아니다.

| 구성 | 요약 구간 | 요약 시간 | 표시 항목 / 원문 확인 |
|---|---:|---:|---:|
| 이전 전체 실행 | 8 | 710.157초 | 61 / 48 |
| 입력 간소화·예산 중심 묶기 | 2 | 150.166초 | 19 / 16 |
| 본문 먼저 생성하는 실험 | 3 | 79.138초 | 6 / 6 |
| 기존 생성 순서·앞 문맥 전달 | 3 | 127.007초 | 14 / 7 |
| ID 선택·보완 입력 수정 전 | 2 | 47.628초 | 16 / 2 |
| 최종 ID 선택·빠진 범위만 보완 | 2 | 53.681초 | 23 / 1 |

처음 네 행의 확인 수는 재서술의 **해석 확인**이고, 마지막 두 행은 발췌의 **구간 선택 확인**이다. 같은 품질 점수가 아니다. 발췌의 모든 원문 인용은 정확히 복사되며, 확인 표시는 선택 범위의 부족을 뜻한다.

**본문 먼저 생성하는 실험은 채택하지 않았다.** 생성은 빨랐지만 인물·사건을 섞고 앞부분을 생략했으며 원문 중심 확인 발췌만 남았다. 관련 스키마 순서 변경 코드는 제거했다.

앞 문맥 전달과 두 ID 선택 행은 완료한 전사 DB의 별도 사본으로 실제 로컬 모델을 다시 호출한 결과다. [재검증 실행기](../experiments/recheck_long_summary.py)는 제품 ASGI API·새 작업·실제 Ollama 모델을 사용하며, 전사나 네이티브 UI를 다시 실행하지 않는다. 모델 digest와 301개 원문 해시를 검증했다. 전체 파일 실행에서는 초기 요약과 전사 처리의 겹침도 각각 15.914초·18.589초 확인했다. GPU 커널의 동시 점유나 첫 토큰 지연은 측정하지 않았다.

**127초 결과도 의미 정확도 통과가 아니다.** 원문 확인 7개 외에 검사에서 통과한 항목에도 실제 행동을 `condition`이나 `expectation`으로 분류하는 오류가 남았다. 앞의 공상·환영 구절을 전달했지만 그 범위를 안정적으로 보존하지 못했다. 최종 결과의 직접 인용되지 않은 원문 103개는 별도로 보존했다. 원문 처리 범위·인용 유효성·의미 보존을 서로 구분해야 한다.

## 승인한 로컬 발췌 방식

사용자가 핵심 원문 발췌를 기본으로 적용하도록 승인했다. 새 로컬 일반 요약은 AI가 중요한 원문 구간의 ID만 고르고 앱이 실제 원문을 복사한다. 주어·가정·조건을 포함하는 앞 문맥을 함께 연결하며, AI가 새 요약 문장·제목·사건 라벨을 붙이지 않는다. 외부 API의 재서술 경로와 이전 작업의 고정 입력·구간 캐시는 유지한다.

- 모델은 현재 입력에서 핵심 ID를 최대 8개 고른다. 알 수 없는 ID·중복·잘못된 형식은 거절한다.
- 앱은 선택한 ID부터 최대 4개의 연속 원문 단위를 연결하고 다음 선택 ID를 넘지 않게 자른다. 앞 문맥은 같은 기록의 30초 이내이며, 다른 출처와 같은 긴 원문의 이전 단위를 합해 총 320자 이하로 제한한다.
- 앞·중간·뒤의 선택이 부족하면 최대 한 번 보완한다. 그래도 빠진 범위는 작은 원문 발췌를 시간순으로 표시하고 ‘구간 선택 확인 필요’를 붙인다.
- 최초 입력이 예산 끝에 맞아도 보완할 수 있도록, 보완 메시지와 허용 ID 스키마는 빠진 범위의 원문만으로 다시 만든다. 처음 선택은 보존하고, 보완 응답의 ID를 전체 원문 위치에 연결한다. 보완 입력 밖의 ID는 거절하며 구간당 호출은 최대 2회다.
- 화면·실패 작업의 완료 구간·Markdown 내보내기에서 발췌 형식을 유지한다. 저장한 발췌를 다시 읽을 때도 모든 인용이 고정 원문의 부분 문자열인지, 표시 본문이 인용들을 그대로 연결한 것인지 검사한다.

범위의 시작·끝을 모델이 고르는 초기 실험은 채택하지 않았다. 실제 긴 입력에서 512·1,024토큰 상한까지 같은 위치에서 멈췄다. 한 줄 출력 지시로 응답을 완료시켜도 최대 4개 단위 제한을 어긴 긴 범위를 골랐다. 짧은 입력에서는 같은 형식이 정상 동작했으므로 엔진이 그 형식을 전혀 지원하지 않는다고 판단하지 않았다. 제품은 기존 ID 배열 형식을 사용하고 범위 확장을 앱이 수행한다.

발췌문이 원문에 있다는 것은 선택한 내용이 가장 중요하다거나 원래 전사가 정확하다는 뜻이 아니다. 앞·중간·후반의 선택 범위는 위치에 따른 점검이며 의미적 완전성 검사가 아니다. 확인이 필요한 선택은 화면과 Markdown에 표시한다.

## 최종 발췌 결과와 남은 한계

최종 실행은 **53.681초·2구간·3회 호출**로 완료됐다. 전체 원문 301개를 처리 범위에 남겼으며, 표시 23항목의 **239개 인용 발생 건이 모두 고정 원문의 부분 문자열**이었다. 서로 다른 직접 인용 출처는 86개이며, 직접 인용하지 않은 215개는 별도로 보존했다. 화면 본문은 인용을 그대로 연결한 문자열이고 생성 주어·사건 라벨은 없었다. 실제 Markdown API의 내보내기 검사도 통과했다.

첫 묶음의 선택이 초반에 몰려 기존 방식은 보완 입력을 추가할 공간이 없었다. 수정 후 빠진 범위의 177개 단위만 보내 보완 호출이 실행됐으며, 여전히 한 범위는 선택이 부족해 원문 확인 발췌를 표시했다. **중요 내용의 선택 문제는 남아 있다.** 이전 오해의 계기가 된 ‘공상과 환영’의 두 원문 조각도 주 발췌에서 선택되지 않아 미인용 원문에 남았다. 이를 주어·가정 내용의 완전한 보존으로 발표하지 않는다. 후반의 남편이 일어나 방으로 들어가고 아내가 뒤따르는 대목은 원문으로 포함됐다.

재서술 모델의 해석 능력이 개선됐다는 결과가 아니다. 새 로컬 기본 경로는 생성 해석을 붙이지 않아 잘못된 주어·가정 설명이 새 문장으로 나타나는 단계를 제거한다. 원래 전사의 오류와 중요한 구간의 선택 누락은 계속 확인해야 한다. 표시 문맥이 겹쳐 같은 원문을 여러 항목에서 볼 수도 있다.

## 최종 검증·설치 앱

- 전체 Python 검사 **362개 통과**(62.674초), 화면 검사 **44개 통과**, TypeScript 검사·Vite 빌드 통과.
- 별도 코드 리뷰에서 발췌·내보내기·캐시·문맥의 집중 검사 33개와 앵커 범위 조합 7,800개를 확인했다. 범위는 최대 4개 현재 단위이며 다음 앵커를 넘지 않았다.
- 설치 앱의 기존 네이티브 실행 파일과 서명은 유지하고 코드·화면 번들을 갱신했다. 정상 종료·재실행 뒤 서버 준비와 최신 화면을 확인했고, 기존 페이지 필기 데이터의 해시가 같았다.
- 이번 실제 마이크 수집은 134.6초다. 수십 분의 마이크 수집·다화자·생활 소음 전체를 이번 변경 후 다시 측정한 결과는 아니다.

## 재현

전체 파일 실행은 기존 검증 실행기를 새 출력 폴더·비어 있는 포트로 실행한다. 완료된 검증 폴더를 사용한 생성만의 비교는 아래와 같다. 준비된 앱 Python 환경과 기존 모델이 필요하며 다운로드는 하지 않는다.

```sh
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$PWD" python experiments/recheck_long_summary.py \
  .local-state/completed-long-run \
  .local-state/new-summary-check
```

완료된 긴 파일 검증 표시가 있는 폴더만 입력으로 받고, 이미 존재하는 출력 폴더는 거절한다. DB 사본·모델 응답 본문·작업 ID·진단용 응답·Markdown은 로컬 검증 폴더에만 남긴다. 공개 JSON은 원음·원문·인증 값·로컬 경로·내부 작업 ID를 제외한 측정값이다. 호스트 부하·메모리·워밍업을 통제하지 않은 단일 실행들이며 재서술에서 발췌로 작업 방식도 바뀌었으므로, 모델의 일반적인 성능 순위나 보편적인 개선율을 주장하지 않는다.
