# Mac 내장 앱의 녹음·복구·동시 실행 검증

2026-10-16. 현재 Apple M4·16GiB·macOS 27.0.1에서 수행한 기록이다. 사용자 실제 보관함과 분리한 복사본을 사용하며, 원음·전사·필기 좌표·화면은 공개 저장소에 포함하지 않는다.

## 범위와 기준

- 실제 마이크의 장시간 입력을 저장하고, 저장 프레임·PCM 패킷 원장·WAV 내용이 일치하는지 확인한다.
- 물리 절전 뒤 실제 입력이 돌아오면 한 번 자동 복구한다. 앞 녹음은 중단 구간으로 보존하며 빠진 벽시각을 숨기지 않는다.
- 검증 앱과 소유 엔진을 SIGKILL한 뒤 재시작해, 디스크에 커밋한 원음과 페이지 버전·초안 내용이 남는지 확인한다. 아직 커밋되지 않은 메모리 입력과 포인터를 놓지 않은 획은 복구 기준에 포함하지 않는다.
- 같은 실제 한국어 음성에서 진행 중인 생성과 전사를 겹치고, 전사 적체 중 새 로컬 생성의 대기·재개를 확인한다.
- 위 검증이 끝난 뒤 코드·검증 기록을 `main`에 반영한다. 미완료 항목은 통과로 표시하지 않는다.

## ACK 대기 중 자동 복구가 종료되는 오류

`WorkerBridge.cancel()`은 취소된 요청의 오류 콜백을 즉시 실행한다. 녹음 종료 큐가 3초 drain 기한을 넘겨 패킷을 취소할 때, 기존 코드는 그 콜백을 원음 저장 실패로 처리해 전체 캡처의 `stop()`에 다시 진입했다. 복구 가능한 절전·ACK 지연이 사용자 종료 상태로 바뀌는 오류다.

실제 `AudioCapture` 클래스를 사용하는 회귀 fixture에서 ACK를 보류한 뒤 절전 복구로 진입시키면 `finished=true`, `waiting=false`, `phase=idle`로 잘못 끝나는 것을 재현했다. 취소 전에 활성 패킷 ID를 무효화하고, 현재 요청과 다른 늦은 콜백은 무시하도록 수정했다. 같은 검사에서 복구 대기를 유지하고, 늦은 ACK가 다음 패킷 상태를 바꾸지 않으며, 명시적 사용자 종료는 끝나는 것을 확인했다.

검사 코드는 `macos/AudioRecoveryFixture.swift`, `tests/test_native_capture.py`다. 실제 수집 장치를 사용하지 않는 실패 경로 검사이며 물리 절전 시험을 대신하지 않는다. 수정 후 전체 백엔드 441개 중 436개 통과·선택적 실제 모델 검사 5개 건너뜀(27.682초), Swift 앱 빌드·서명 검사도 통과했다.

## 강제 종료의 기본 복구 확인

수정 전 v5 검증 앱에서 실제 마이크 입력 중 PDF 메모와 포인터를 놓은 필기를 저장한 뒤, 앱과 해당 앱의 엔진 프로세스 그룹만 SIGKILL했다. 제품 앱은 시험 대상에 포함하지 않았다.

재시작 후 중단된 녹음은 289.2초·48kHz·13,881,600프레임으로 보존됐고 화면에 `마이크 · 중단`으로 표시됐다. 종료 전에 기준으로 저장한 원음 7개의 PCM 앞부분과 페이지 버전 13개는 그대로였다. 각 패킷의 실제 PCM과 DB SHA256도 일치했다. 페이지 메모·필기 v6이 화면에 다시 보였다.

이때 기준 시점의 미저장 dirty 초안은 0개였다. 따라서 이 결과만으로 충돌 상태의 미저장 초안이나 진행 중인 획까지 검사했다고 해석하지 않는다. DB 커밋은 앱이 ACK를 수신했다는 증거와도 구분한다.

## 실제 긴 음성의 전사·생성 동시 실행

기존에 받은 [LibriVox 『술 권하는 사회』 Part 1](https://archive.org/download/short_stories_hyun_1411_librivox/short_stories_02_hyun_128kb.mp3) 한국어 사람 낭독 MP3를 읽기 전용으로 재사용했다. 원음 길이는 878.303492초다. 새 다운로드나 외부 API 호출은 없었다.

하나의 실제 내장 파이프 엔진에서 다음 순서로 실행했다.

1. 원음 전체를 Whisper large-v3-turbo로 단독 전사한다.
2. 그 전사의 긴 Qwen3.5 4B 요약을 시작하고 실제 모델 프로세스가 실행된 뒤 같은 원음의 두 번째 전사를 제출한다.
3. 확정 전사가 밀린 동안 요약을 하나 더 제출해 대기·재개를 확인한다.

| 관찰 | 결과 |
| --- | --- |
| 단독 전사 작업 생성→완료 | 97.032초 |
| 진행 중인 생성과 겹친 전사 | 119.373초 |
| 두 전사의 완료 범위·문장 | 각각 33개 범위·301문장 |
| 전사 텍스트와 시작·끝 시각 | 두 결과 모두 동일 |
| 원음 프레임 범위 | 0–38,733,184프레임을 연속 처리 |
| 실제 Qwen·Whisper 프로세스 겹침 | 모니터링 9개 표본 |
| 적체 뒤 제출한 요약 | `전사 처리 후 실행` 대기 후 재개·완료 |
| 긴 요약 두 건 | 각각 문맥 2개·원문 발췌 22개, 처리 원문 301개·직접 인용 94개 |
| 인용·후반 처리 | 모든 인용이 실제 원문과 일치. 876,820ms까지 처리 |
| 네트워크·종료 | 프로세스 표본 97개에서 소켓 없음. 종료 코드 0·잔여 소유 자식 0 |
| 원본 음성과 모델 | 크기·mtime·SHA256 유지 |

진행 중이던 생성은 현재 모델 호출을 마친 뒤 다음 호출 전에 전사 적체를 기다렸고, 뒤에 제출한 생성도 적체 해소 뒤 실행됐다. 이 조건에서 작업 누락·실패는 재현되지 않았다.

각 조건은 한 번씩 실행했으며, 실제 마이크 입력이 같은 Mac에서 별도로 진행됐다. 공유 호스트의 워밍·swap 영향을 포함하므로 두 시간을 일반적인 성능 비율이나 서버 제거의 속도 향상으로 해석하지 않는다. 최대 표본 프로세스 그룹 RSS는 약 3,250MiB였으며 GPU 전체 메모리의 피크 측정치는 아니다.

문학 낭독은 다화자 회의나 정답 시각이 있는 전사 자료를 대표하지 않는다. 두 결과가 같다는 것은 정답과 같다는 뜻이 아니므로 CER·누락률·환각률을 제시하지 않는다. 원문 발췌 인용의 일치는 확인했지만 선택한 발췌의 의미적 완전성을 보장하지 않는다.

## 장시간 수신의 메모리 누적

v6의 실제 마이크 입력을 541.5초 저장했다. 앱 RSS는 녹음 중 121,504→236,720KiB로 늘었고, 520초 표본의 기울기는 약 12.90MiB/분이었다. 엔진 RSS는 약 136MiB로 유지됐다. 앱 heap에서 16KiB `NSConcreteData` 버퍼와 JSON 임시 객체가 누적되는 것을 확인했다.

`WorkerBridge.read()`는 엔진 종료까지 하나의 Dispatch 작업으로 실행된다. 각 수신 반복을 `autoreleasepool`로 감싸 Foundation 임시 객체를 그 반복에서 해제하도록 수정했다. 실제 `WorkerBridge`로 5,000회 요청·ACK를 주고받는 검사에서, 500회 시점 대비 메모리 증가는 수정 전 96,436,224B로 24MiB 한도를 초과했고 수정 후 49,152B로 통과했다. 검사 파일은 `macos/WorkerMemoryFixture.swift`, `tests/test_native_bridge_memory.py`다. 실제 수정 앱의 30분 메모리 추이는 별도로 확인한다.

v6에서 원본 입력 시간축의 1.031229초 공백도 한 번 관찰됐다. 저장된 PCM은 연속 보존됐고 빠진 시간은 `gaps`와 화면에 표시됐다. 같은 시각 앱 heap 조사 도구가 2.78초 실행됐으며, CoreAudio는 약 2.60초의 클라이언트 IO 기한 초과와 입력 sample time 불연속을 기록했다. 패킷 순번은 연속이어서 패킷 생성 전 입력 시각이 뛴 것으로 범위를 좁혔다. heap 조사의 계측 간섭이 강한 원인 후보지만 단독 원인으로 확정하지 않는다. 이후 실제 캡처에서는 앱을 일시 정지시킬 수 있는 heap·vmmap·디버거 조사를 제외한다.

## 남은 실제 장치 검사

- [ ] ACK 수정본의 30분 이상 실제 마이크 입력
- [ ] 물리 절전·복귀와 새 녹음 구간의 자동 복구
- [ ] 수정본의 강제 종료 후 원음·필기 및 dirty 초안 복구
- [ ] 제품 앱 갱신·원본 보존 대조·`main` 반영

v6에서 새 마이크 권한 응답이 늦는 동안 합의한 30초 연결 제한이 실행됐다. 사용자가 권한을 허용한 뒤에도 취소된 요청으로 녹음이 시작되지 않았고, 녹음 시작을 다시 눌렀을 때 정상 입력을 받았다. 이후 위 메모리 누적을 발견해 9분 기준을 보존하고 앱을 정상 종료했다. 두 수정이 포함된 v7에서 장시간·절전·강제 종료 시험을 수행한다. 시스템 권한 창을 우회하거나 TCC 저장소를 변경하지 않는다.

대기 중에는 복사본에서 동일한 제품 저장 함수를 두 번째 SQLite 연결로 호출해 페이지 버전을 올린 뒤, 이전 버전을 보고 있던 UI에서 편집해409충돌을 만들었다. 화면의 `충돌 · 초안 보존`과 native SQLite의 dirty본문·저널2행을 확인했다. 이 초안을 실제 강제 종료 뒤 복구하는 검사는 아직 남아 있다.
