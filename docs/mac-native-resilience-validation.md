# Mac 내장 앱의 녹음·복구·동시 실행 검증

2026-10-16–17. 현재 Apple M4·16GiB·macOS 27.0.1에서 수행한 기록이다. 사용자 실제 보관함과 분리한 복사본을 사용하며, 원음·전사·필기 좌표·화면은 공개 저장소에 포함하지 않는다.

## 범위와 기준

- 실제 마이크의 장시간 입력을 저장하고, 저장 프레임·PCM 패킷 원장·WAV 내용이 일치하는지 확인한다.
- 물리 절전 뒤 실제 입력이 돌아오면 한 번 자동 복구한다. 앞 녹음은 중단 구간으로 보존하며 빠진 벽시각을 숨기지 않는다.
- 검증 앱과 소유 엔진을 SIGKILL한 뒤 재시작해, 디스크에 커밋한 원음과 페이지 버전·초안 내용이 남는지 확인한다. 아직 커밋되지 않은 메모리 입력과 포인터를 놓지 않은 획은 복구 기준에 포함하지 않는다.
- 같은 실제 한국어 음성에서 진행 중인 생성과 전사를 겹치고, 전사 적체 중 새 로컬 생성의 대기·재개를 확인한다.
- 위 검증이 끝난 뒤 코드·검증 기록을 `main`에 반영한다. 미완료 항목은 통과로 표시하지 않는다.

## ACK 대기 중 자동 복구가 종료되는 오류

`WorkerBridge.cancel()`은 취소된 요청의 오류 콜백을 즉시 실행한다. 녹음 종료 큐가 3초 drain 기한을 넘겨 패킷을 취소할 때, 기존 코드는 그 콜백을 원음 저장 실패로 처리해 전체 캡처의 `stop()`에 다시 진입했다. 복구 가능한 절전·ACK 지연이 사용자 종료 상태로 바뀌는 오류다.

실제 `AudioCapture` 클래스를 사용하는 회귀 fixture에서 ACK를 보류한 뒤 절전 복구로 진입시키면 `finished=true`, `waiting=false`, `phase=idle`로 잘못 끝나는 것을 재현했다. 취소 전에 활성 패킷 ID를 무효화하고, 현재 요청과 다른 늦은 콜백은 무시하도록 수정했다. 같은 검사에서 복구 대기를 유지하고, 늦은 ACK가 다음 패킷 상태를 바꾸지 않으며, 명시적 사용자 종료는 끝나는 것을 확인했다.

검사 코드는 `macos/AudioRecoveryFixture.swift`, `tests/test_native_capture.py`다. 실제 수집 장치를 사용하지 않는 실패 경로 검사이며 물리 절전 시험을 대신하지 않는다. 수정 후 전체 백엔드 441개 중 436개 통과·선택적 실제 모델 검사 5개 건너뜀(27.682초), Swift 앱 빌드·서명 검사도 통과했다.

## 강제 종료의 기본 복구 확인

수정 전 v5 검증 앱에서 실제 마이크 입력 중 PDF 메모와 포인터를 놓은 필기를 저장한 뒤, 앱과 해당 앱의 엔진 프로세스 그룹만 SIGKILL했다. 제품 앱은 시험 대상에 포함하지 않았다.

재시작 후 중단된 녹음은 289.2초·48kHz·13,881,600프레임으로 보존됐고 화면에 `마이크 · 중단`으로 표시됐다. 종료 전에 기준으로 저장한 원음 7개의 PCM 앞부분과 페이지 버전 13개는 그대로였다. 각 패킷의 실제 PCM과 DB SHA256도 일치했다. 페이지 메모·필기 v6이 화면에 다시 보였다.

이때 기준 시점의 미저장 dirty 초안은 0개였다. 따라서 이 결과만으로 충돌 상태의 미저장 초안이나 진행 중인 획까지 검사했다고 해석하지 않는다. DB 커밋은 앱이 ACK를 수신했다는 증거와도 구분한다.

## 실제 긴 음성의 전사·생성 동시 실행

기존에 받은 [LibriVox 『술 권하는 사회』 Part 1](https://archive.org/download/short_stories_hyun_1411_librivox/short_stories_02_hyun_128kb.mp3) 한국어 사람 낭독 MP3를 읽기 전용으로 재사용했다. 원음 길이는 878.303492초다. 새 다운로드나 외부 API 호출은 없었다.

하나의 실제 내장 파이프 엔진에서 다음 순서로 실행했다.

1. 원음 전체를 Whisper large-v3-turbo로 단독 전사한다.
2. 그 전사의 긴 Qwen3.5 4B 요약을 시작하고 실제 모델 프로세스가 실행된 뒤 같은 원음의 두 번째 전사를 제출한다.
3. 확정 전사가 밀린 동안 요약을 하나 더 제출해 대기·재개를 확인한다.

진행 중이던 생성은 현재 모델 호출을 마친 뒤 다음 호출 전에 전사 적체를 기다렸고, 뒤에 제출한 생성도 적체 해소 뒤 실행됐다. 이 조건에서 작업 누락·실패는 재현되지 않았다.

각 조건은 한 번씩 실행했으며, 실제 마이크 입력이 같은 Mac에서 별도로 진행됐다. 공유 호스트의 워밍·swap 영향을 포함하므로 두 시간을 일반적인 성능 비율이나 서버 제거의 속도 향상으로 해석하지 않는다. 최대 표본 프로세스 그룹 RSS는 약 3,250MiB였으며 GPU 전체 메모리의 피크 측정치는 아니다.

문학 낭독은 다화자 회의나 정답 시각이 있는 전사 자료를 대표하지 않는다. 두 결과가 같다는 것은 정답과 같다는 뜻이 아니므로 CER·누락률·환각률을 제시하지 않는다. 원문 발췌 인용의 일치는 확인했지만 선택한 발췌의 의미적 완전성을 보장하지 않는다.

기존 강의 요약은 새 MP3 전사의 품질 정답으로 사용하지 않는다. 첫 요약은 61.618초, 전사 대기와 재개를 포함한 두 번째 요약은225.127초였다. 모델 내부 측정값도 대기를 포함하므로 순수 추론 시간으로 표시하지 않는다. 이미 시작한 생성 호출은 끝났고, 다음 생성 호출은 다시 전사 적체를 기다렸다.

동시 프로세스 존재는 GPU 커널의 동시 실행 측정이 아니다. 인용의 원문 일치와 처리한 후반 범위는 확인했지만, 중요한 발췌의 선택이 완전한지까지 정답 평가한 결과는 아니다.

## 장시간 수신의 메모리 누적

v6의 실제 마이크 입력을 541.5초 저장했다. 앱 RSS는 녹음 중 121,504→236,720KiB로 늘었고, 520초 표본의 기울기는 약 12.90MiB/분이었다. 엔진 RSS는 약 136MiB로 유지됐다. 앱 heap에서 16KiB `NSConcreteData` 버퍼와 JSON 임시 객체가 누적되는 것을 확인했다.

`WorkerBridge.read()`는 엔진 종료까지 하나의 Dispatch 작업으로 실행된다. 각 수신 반복을 `autoreleasepool`로 감싸 Foundation 임시 객체를 그 반복에서 해제하도록 수정했다. 실제 `WorkerBridge`로 5,000회 요청·ACK를 주고받는 검사에서, 500회 시점 대비 메모리 증가는 수정 전 96,436,224B로 24MiB 한도를 초과했고 수정 후 49,152B로 통과했다. 검사 파일은 `macos/WorkerMemoryFixture.swift`, `tests/test_native_bridge_memory.py`다. 실제 수정 앱의 30분 메모리 추이는 아래 장시간 수신 기록에서 확인한다.

v6에서 원본 입력 시간축의 1.031229초 공백도 한 번 관찰됐다. 저장된 PCM은 연속 보존됐고 빠진 시간은 `gaps`와 화면에 표시됐다. 같은 시각 앱 heap 조사 도구가 2.78초 실행됐으며, CoreAudio는 약 2.60초의 클라이언트 IO 기한 초과와 입력 sample time 불연속을 기록했다. 패킷 순번은 연속이어서 패킷 생성 전 입력 시각이 뛴 것으로 범위를 좁혔다. heap 조사의 계측 간섭이 강한 원인 후보지만 단독 원인으로 확정하지 않는다. 이후 실제 캡처에서는 앱을 일시 정지시킬 수 있는 heap·vmmap·디버거 조사를 제외한다.

## 30분 실제 마이크와 중간 보존 대조

v7 앱에서 실제 마이크 입력을 시작하고, 위 UI 동시 실행과 파일 선택·초안 내보내기를 포함해 하나의 녹음 구간을 유지했다. 절전 전 기준점은 **1,825.8초·48kHz·87,638,400프레임·18,258패킷**이었다. 입력·저장 프레임이 일치하고 `gaps`는 비어 있었다. 모든 커밋한 패킷의 실제 PCM SHA256과 원장을 대조했다.

22분 시점과 위 기준점을 비교해 마이크 원음9개의 기존 PCM 앞부분, 페이지 버전14개, dirty 초안3행의 내용이 보존된 것을 확인했다. 현재 편집한 초안은119자·필기4획이며, 실제 앱의 저장 창으로 JSON을 내보내 같은 내용을 확인했다. 충돌 상대본을 선택하거나 원래 저장 버전을 덮어쓰지 않았다.

30분 관찰 중 앱 RSS 표본의 최대는105,968KiB였다. 초기 준비 뒤 수정 전의 분당12.90MiB 증가 패턴은 재현되지 않았다. RSS에는 OS 압축·페이징이 영향을 주며 GPU 전체 메모리와 launchd 소속 WebKit 서비스는 포함하지 않는다. 따라서 이 수치만으로 모든 종류의 메모리 누수가 없다고 결론내리지 않는다.

## 실제 절전·복귀와 강제 종료 복구

시스템 전원 로그에서 23:35:41–23:36:03 KST의 실제 절전22초를 확인했다. 절전 전 구간은1,912.6초·91,804,800프레임으로 중단 사유와 함께 보존됐다. 복귀 후 같은 캡처의 새 구간이 자동 생성됐고 실제 입력이 계속 저장됐다. UI에는 `자동 복구됨 · 녹음 중`이 표시됐다. 두 구간 사이27,988ms는 녹음 오프셋에 보존하며 원음을 이어 붙여 숨기지 않았다.

복귀한 새 구간을89.3초 이상 저장한 뒤 기준을 만들고, 정확한 실행 경로·보관함·소유 프로세스 그룹을 확인해 검증 앱과 엔진에만 SIGKILL했다. 같은 앱을 재시작한 뒤 새 구간은101.1초·4,852,800프레임의 중단 원음으로 복구됐다. 기존 PCM 앞부분10개·페이지 버전14개와 dirty 초안3행의 키·본문·잉크가 보존됐고 모든 저장 패킷의 PCM SHA256도 원장과 일치했다.

복원된 페이지에서 메모와 필기가 보였고, 강제 종료 전후 실제 UI에서 내보낸 JSON은2382바이트·119자·4획으로 같았으며 파일 SHA256도 같았다. 복구한 초안을 UI에서 새v8로 저장한 뒤 이전v7·충돌 해결 전 사본이 남는 것도 확인했다. 아직 놓지 않은 획이나 커밋되지 않은 입력의 복구를 보장하는 검사는 아니다.

전체 마이크 원음은 절전 전1,912.6초와 복귀 후101.1초, 합계2,013.7초다. 239개 모니터 표본에서 프로세스·DB 조회 오류와 소유 프로세스의 소켓 관찰은0건이었다. 모니터의 복귀 시각 표본 공백26.132초와 실제 전원 로그의 절전22초는 다른 측정값이다.

## 실제 앱 갱신과 기존 데이터 보존

기존 제품 앱을 정상 종료한 뒤43개 테이블·86개 스키마 객체 전체의 기준을 만들었다. native 초안과 설정도 제외하지 않았다. 최신 보관함의 로컬 백업은 일반 파일29개·214,790,319바이트를 해시 대조하고 심볼릭 링크를 보존했다.

`~/Applications/Solasi.app`을0.3.1/build11로 갱신했다. 이전 앱 번들은 별도 백업으로 남겼고 legacy 초안 import를 다시 실행하지 않았다. 기존 `data/runtime` 경로를 유지하며 `source/python/port` 실행 설정은 없다. 설치 후 실제 과목3개·PDF 원본·기존 메모v2·필기 표시를 확인하고 정상 종료했다. 설치 직전과 실행·종료 뒤 모두43개 테이블과 파일 참조18개의 내용이 기준과 같았으며 누락 원본은0개였다.

## 추가로 발견한 Whisper 문자 출력 오류

강제 종료 복구 후31분 원음의 자동 전사를 확인하다68개 범위 중67개 완료·1개 실패를 발견했다. 실패한25.16초 원음을 같은 동봉 Whisper·기본 VAD 설정으로 한 번 더 실행해, 종료 코드0이어도 결과 JSON의 전사 문장 하나에 잘못된 UTF-8 바이트가 나오는 것을 재현했다. 원음 해시는 같았으며 패킷 저장 손상과 구분했다.

VAD를 끈 기존 후보 설정은 같은 원음에서 UTF-8·시각 형식을 통과했지만, 정답 전사 대조를 하지 않아 더 정확한 결과로 채택하지 않았다. 기본 결과의 문자를 `replace/ignore`로 바꿔 저장하지 않는다. 사용자는 grilling 검토에서 이 형식 오류도 기존의 최대1회 재인식 후보·사용자 적용 경로에 연결하는 정책을 승인했다. 엄격한 UTF-8 오류만 대상으로 삼고 준비된 Qwen을 우선하며, 준비되지 않았으면 기존 VAD 없는 Whisper 후보를 사용한다. 원래 상태·실패 이유를 후보 요청에 보존하고, 생성만으로 실패 상태를 바꾸지 않는다. 적용 시에도 별도의 원음 읽기·범위 계획 실패를 완료로 지우지 않도록 검사한다. 이 후속 변경은 아래 실제 확인을 마친 새 엔진 빌드에 포함하며, 앞서 설치한0.3.1/build11에는 포함되지 않는다.


## 같은 오류 원음의 최종 내장 앱 검증

0.3.2/build12 검증 앱은 최종 `frozen-engine-v7`과 새 화면을 포함한다. 이전 원시 디코딩 오류가 남은 녹음의 `전사 재시도`를 실제 UI에서 눌러 실패했던25.16초 범위만 다시 처리했다. 같은 엄격한 UTF-8 오류가 재현됐고, 화면에 `전사 출력 오류 · 원음 확인 필요`가 표시됐다. 원음 재생을 누르면 해당 범위의 저장 위치665.2초에서 시작했으며 재생 위치가 진행한 뒤 일시 정지했다. 스피커 음성을 직접 청취한 정확도 검사는 아니다.

설치된 Qwen3-ASR-1.7B 4bit가 자동 후보 한 건을 생성했다. 결과는28자·19생성토큰이었으며 MLX 피크 할당은2,680,526,140바이트였다. 후보가 완료돼도 해당 범위와 부모 작업은 실패 상태이고 저장된 인식문은0개였다. 실제 화면에서 `확인한 전사 적용`을 누른 뒤에만 해당 범위가 완료·오류 없음으로 바뀌고 부모 집계가68개 완료·실패0개로 정리됐다. 원래 실패 상태·이유는 후보 요청에 남았다.

적용 전후 기존 정상67개 범위의297문장, 기존 출처, 원음 WAV, 페이지 문서와 native 초안의 해시가 모두 같았다. 오류 카드가 사라지고 후보에 `적용됨`이 표시되는 것과 정상 종료·엔진 회수도 확인했다. 이 적용은 격리된 검증 보관함에서 저장·상태 처리 흐름을 검사한 것이며, 후보28자의 정답을 승인하거나 품질 향상을 확정한 결과가 아니다.

최종 검토에서 후보 적용이 뒤늦게 발생한 별도의 원음 읽기·범위 계획 실패까지 완료로 바꿀 수 있는 경계를 발견해 수정했다. 실제 임시 WAV 뒷부분을 자른 뒤 범위 계획 오류와 후보 적용을 결합한 회귀로 실패 이유 보존을 확인했다. 전체 백엔드452개 중447개 통과·선택 검사5개 건너뜀(27.322초), 프런트엔드71개와 TypeScript·Vite 빌드가 통과했다. 설치된 화면5개 파일도 새 빌드와 해시가 같았다.

## 최종 제품 갱신과 재대조

2026-10-17 00:09 KST에 실제 `~/Applications/Solasi.app`을 **0.3.2/build12**로 갱신했다. 동봉 엔진은 위 실제 후보 생성·적용 검사를 통과한 `frozen-engine-v7`이며 실행 파일 SHA256은 `e441ec6cb7900bf34e5fcab35fbf5cc80eea24bb28ae878aa9d3561da49a4f6c`다. 이전0.3.1 앱은 별도 번들 백업으로 보존했다. 기존 보관함을 다시 가져오거나 합치지 않았다.

- 실제 홈의 과목3개, PDF 원본1쪽, 저장된 메모v2와 잉크 표시를 직접 확인했다. 검증용 녹음·후보·필기는 실제 보관함에 섞지 않았다.
- 설치 직전과 최종 앱 실행·정상 종료 후 모두43개 테이블·86개 스키마 객체, 연결 원본18개의 내용이 기준과 같았다. native 초안·설정도 제외하지 않았으며 SQLite integrity검사는`ok`, 외래 키 오류·누락 원본은0개였다.
- 실행 설정은 이전과 같은 `data/runtime` 두 경로만 가진다. 새 화면 파일5개의 해시가 실제 동봉 화면과 같았고, Swift 빌드·엄격한 서명 검사·frozen 자체 검사를 통과했다.
- 실제 제품 앱과 소유 엔진의 표본에서 Internet 소켓이 없었다. ⌘Q 뒤 두 프로세스가 모두 종료됐고 보존 대조도 통과했다. 이 한 표본을 연속 네트워크 감시로 해석하지 않는다.

Swift 녹음·브리지 소스는 v7 하드웨어 시험 뒤 바뀌지 않았다. 후속 Python 오류·후보 처리는 같은25.16초 원음과 최종 동봉 엔진에서 별도로 확인했다. 제품 최종 패키지로30분 절전을 다시 수행한 결과로 합쳐 표시하지 않는다.
