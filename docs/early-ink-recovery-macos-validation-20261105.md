# Mac 진행 중 필기 복구 개선과 검증

2026-11-05. 실제 설치 앱 **Solasi 0.3.40 / build 50**, **680×480** 창에서 라이트·다크를 확인했다. 캡처는 1360×960이다. 기존 기록과 분리된 검증 과목의 PDF 1쪽을 사용했다.

## 달라진 동작

기존에는 펜·형광펜의 획을 마쳐야 복구 초안을 만들었다. 그리는 중인 획은 화면 메모리에만 있어 해당 시점의 강제 종료를 보호하지 못했다. 획을 마친 뒤에도 native upload 생성·조각 전송·commit이 끝나기 전까지 기록 공백이 있었다.

이제 펜·형광펜의 첫 점은 바로 별도 복구 journal 쓰기를 요청하고, 진행 중 좌표는 250ms 간격을 기준으로 최신 값만 합쳐 기록한다. 한 번의 쓰기가 진행 중이면 최신 요청 하나만 대기시킨다. 화면 그리기와 확정 페이지 저장은 이를 기다리지 않는다.

이 journal은 기존 메모·필기·확정 페이지와 분리된다. 재실행하면 **‘그리던 획 복구 후보’**의 미리보기와 적용 버튼으로 제공한다. 사용자가 적용하기 전에는 확정 페이지·인식·검색에 편입하지 않는다. 정상적으로 끝낸 획은 기존처럼 실행 취소 한 번으로 돌아가며, 최종 초안이 기록된 뒤 해당 임시 journal을 정리한다. Escape·pointercancel 등 입력 취소 의미는 유지한다.

서로 다른 기준의 후보를 적용할 때는 현재 미저장 편집과 이전 보관 사본을 독립적으로 보존하고 기존 충돌 비교를 거친다. 저장 응답을 기다리는 동안에는 후보 적용을 보류해 뒤늦은 응답이 비교 단계를 건너뛰지 못하게 했다. 현재 필기 뒤에 부분 획만 추가하는 호환 가능한 적용은 기존 backup을 바꾸지 않는다.

## 작은 초안의 기록 경로

64KiB 이하의 native 초안은 한 번의 원자적 요청으로 기록한다. 이전의 upload 생성 → 조각 전송 → commit 세 요청을 줄인 것이다. 그보다 큰 초안과 가져오기는 기존 크기 검사·조각 ACK·commit 경로를 유지한다. JavaScript의 `1e-7`과 Python의 `1e-07`처럼 재직렬화한 크기가 커져 직접 저장을 거절당한 경우에도 조각 전송으로 이어간다. 이 특정 422 크기 오류만 전환하며 디스크 오류 등 다른 실패는 그대로 알린다. 일반 초안 쓰기와 journal-only checkpoint 쓰기는 같은 검증·트랜잭션 코드를 사용한다.

별도의 임시 DB에서 같은 2,507바이트 입력을 경로별 40회씩 번갈아 실행했다. SQLite commit은 **3회 → 1회**, 중앙값은 **0.525ms → 0.169ms**였다. 이 수치는 같은 프로세스 안의 native 저장 동작만 측정한 값이며 bridge·화면 응답을 포함한 앱 전체 지연이 아니다. 첫 기록 전 유실 가능성이 사라졌다는 뜻도 아니다.

## 실제 설치 앱의 종료·복구 시험

자동 도구의 20초 누름 유지 입력을 사용했다. 새 부분 획 journal은 pointerdown 경로가 실행돼야 생긴다. 감시기는 그 journal과 기존 확정 페이지·canonical 초안을 확인한 뒤 정확한 Solasi PID 하나에 SIGKILL을 보냈다. 앱 소유 엔진이 끝난 뒤에도 확정 페이지와 기존 초안이 변하지 않았는지 다시 대조했다.

| 시험 | 종료 뒤 확정 상태 | 별도 후보 | 사용자 적용 뒤 |
| --- | --- | --- | --- |
| 다크 · 펜 누름 유지 | v7 · 기존 5획 | 6획, 새 펜은 1점 | v8 · 후보의 ink 전체와 일치 |
| 라이트 · 형광펜 누름 유지 | v8 · 기존 6획 | 7획, 새 형광펜은 1점 | v9 · 후보의 ink 전체와 일치 |
| 최종 화면 코드 · 라이트 펜 재시험 | v13 · 기존 7획 | 8획, 새 펜은 1점 | v14 · 후보의 ink 전체와 일치, 기존 backup도 정확히 유지 |

입력 요청부터 SIGKILL까지는 각각 1.268초·0.532초·0.807초로, 요청한 20초 누름이 끝나기 전이었다. 이는 도구 호출 시점부터의 시간이며 실제 입력 시작 지연이나 유실 시간 상한을 측정한 수치가 아니다. 세 경우 모두 재실행해 후보를 펼친 뒤에도 적용 전 페이지는 기존 revision이었다. 메모와 획 ID·도구·색·굵기·불투명도·입력 속성·좌표를 파싱한 값 전체로 비교했다.

정상 완료한 형광펜 직선도 별도로 입력했다. v9의 7획이 v10의 8획이 된 뒤, 실행 취소 한 번으로 v11의 기존 7획과 정확히 같아졌다. 완료 뒤 진행 중 journal은 남지 않았다. 이후 짧은 드래그 시험도 종료 조건보다 자동 저장이 먼저 끝나 해당 종료 시험에서 제외했고, 실행 취소해 원래 7획을 유지했다. 최종 크기 경계 보완을 설치한 뒤에도 v14의 8획에 펜 획 하나를 더해 v15의 9획으로 저장하고, 한 번의 실행 취소로 v16의 원래 8획과 정확히 같아지는 것을 확인했다. 정상 종료·새 프로세스 재실행 뒤에도 같은 v16·메모·전체 ink였다.

680×480의 두 테마에서 도구·저장 상태·복구 후보 미리보기·적용 동작을 확인했다. 긴 복구 목록은 노트 영역을 스크롤해 버튼에 접근할 수 있었다. 마지막에는 기존 다크 모드·지우개·과목 목록·보기 설정을 복원했다.

## 자동 검사와 검토

- 다른 OS의 작업 중 변경을 제외한 clean HEAD 스냅샷에 이번 파일만 덧씌워 빌드했다.
- 프런트엔드 140개 검사와 TypeScript·production build가 통과했다.
- native draft 19개·내장 runtime 6개·native 창 1개 검사가 통과했다. 원자적 실패 보호, 크기·키·요청 형식, 숫자 표기로 커지는 64KiB 경계의 일반 쓰기·checkpoint fallback도 포함한다.
- 느린 쓰기 중 최신 좌표 합치기, 미완성 획의 page PUT 방지, 정상 완료·취소, 오래된 revision의 비교, 저장 중 적용 차단, 현재 편집과 기존 backup의 독립 보존을 검사했다.
- 독립 코드 검토에서 발견한 복구 충돌 시 편집 유실과 지연된 저장 응답의 경합을 수정하고 회귀 검사·재검토를 마쳤다.
- frozen 엔진 self-check, 배포 manifest·앱 서명 검사가 통과했다. 마지막 화면 보완은 기존 native 실행 코드·엔진·launch 경로를 유지한 채 반영했다.

## 기존 데이터 보존

시험 시작 전에 일관된 SQLite 백업과 내부 파일 해시를 보존했다. 기록·출처·필기 관련 12개 테이블의 기존 **4,195행** 중 **4,192행이 그대로**다. 변경된 세 행은 검증 페이지의 현재 revision(v6 → v16), 해당 canonical 초안 값, 이전 OCR 후보의 stale 상태뿐이다. 기존 revision·출처·다른 writer의 복구 사본은 유지됐다.

내부 보관 파일 **73개**의 크기·SHA256이 일치했고, 외부 검증 PDF 원본도 별도로 해시를 대조했다. 이 파일 수는 외부 연결 원본 전체의 목록이 아니다. SQLite 무결성 검사는 `ok`이며 native 도구·테마·노트 보기·목록 설정도 기준값과 같았다. 검사한 테이블은 courses, sessions, sources, notes, recordings, transcript_ranges, transcripts, page_documents, page_document_revisions, native_drafts, ink_recognitions, assets다. 백그라운드 색인·작업 큐 전체의 불변을 의미하지 않는다.

원음·필기·DB·캡처는 공개 저장소에 포함하지 않는다. 로컬 증거는 `.local-state/early-ink-crash-20261105/`의 각 `*-killed.json`, `*-candidate.json`, `*-applied.json`, `final-backup-preserved.json`, `normal-completed.json`, `normal-undo.json`, `after-normal-quit.json`, `after-final-restart.json`, `final-relaunch-process.json`, `FINAL-VERIFICATION.json`에 남겼다. 수동 입력 감시기는 사용자가 직접 조작하기 어렵다고 답한 뒤 해제했다.

## 유실 범위와 미확인 사항

실제 앱에서 확인한 것은 **입력을 아직 놓지 않은 상태의 한 점을 별도 후보로 보존하는 경로**다. 자동 드래그는 두 점만 빠르게 전송해 연속 곡선의 종료 시험을 충분히 만들지 못했다. 사용자의 직접 입력도 이번에는 어려워 **여러 점을 계속 그리는 도중의 실제 곡선 종료·복구는 미확인**이다. 여러 점의 최신 좌표 합치기·정확한 데이터 보존은 자동 검사로 확인한 범위다.

첫 durable journal 전에 도착하지 않은 입력은 복구할 수 없다. 실제 비교에서도 초안 전송 시작 시 앱을 종료했지만 worker가 이미 접수한 쓰기를 끝낸 사례가 있어 이를 ‘기록 전 유실’로 세지 않았다. 기록 요청 전에 종료한 것으로 보이는 누름 시도도 pointerdown 실행 증거가 부족해 중간 획 유실 사례로 세지 않았다. 따라서 수정 전후의 실제 유실 시간을 초·비율로 산정하지 않았다.

마지막으로 기록된 지점 뒤의 점도 유실될 수 있다. 250ms는 합치기 기준이며 디스크·bridge 지연을 포함한 유실 상한이 아니다. 실제 스타일러스 필압·전원 차단·저장 장치 고장·장시간 녹음·OCR 정확도는 이번 변경의 재시험 범위에 포함하지 않았다.

캡처 도구의 noWindowsAvailable·창 변경 감지 때문에 일부 조작을 다시 확인했다. 창을 다시 획득하고 기존 ‘Solasi 열기’로 활성화한 뒤 재시도했으며, 해당 도구 오류를 영구 수정했다고 주장하지 않는다.
