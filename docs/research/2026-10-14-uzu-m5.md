# Uzu의 M5 성능 주장과 현재 M4 앱 적용 검토

확인일: 2026-10-14 (Asia/Seoul)

범위: Mirai 공식 문서·성능표·공식 Hugging Face 메타데이터·Uzu **0.6.3** 소스와 바이럴 실험 원저자의 기록 조회. 패키지 설치, 모델 가중치 다운로드, 서버 기동, 추론·벤치마크, 제품 코드 변경은 수행하지 않았다. 현재 앱의 M4 / 16 GiB, whisper.cpp large-v3-turbo, 앱 소유 Ollama v0.40.3, Qwen3.5:4b MLX와 EmbeddingGemma 구성은 전달받은 작업 전제다. 이 조사에서 실제 설치나 실행 상태를 재검증하지 않았다.

## 판단

**Uzu의 M5 가속은 모델·투기적 디코딩 조건이 붙는다. 현재 M4 / Qwen3.5 4B 앱의 3~4배 개선 근거는 없다.** 공식 4B/M4 출력 차이 약 **0.47%**는 산술 차이이며 통계적 유의성은 미확인이다. [공식 성능표](https://trymirai.com/metrics)

Uzu 0.6.3은 텍스트 생성·JSON Schema·요청 취소 구현을 갖고 있다. 그러나 확인한 HTTP 서버는 이미지 content part를 거부하며, 임베딩 endpoint와 Ollama의 manifest digest 응답도 제공하지 않는다. 따라서 현재 앱의 런타임 전체를 바꾸는 직접 대체재로 확정할 수 없다. 아래의 고정 버전 소스와 기능별 표를 근거로, 우선 조사 후보로 남기는 판단이다. [서버 입력](https://github.com/trymirai/uzu/blob/0.6.3/crates/legacy/cli/src/server/chat_completions.rs#L43-L68), [라우트](https://github.com/trymirai/uzu/blob/0.6.3/crates/legacy/cli/src/server/runner.rs#L232-L236), [모델 응답](https://github.com/trymirai/uzu/blob/0.6.3/crates/legacy/cli/src/server/models.rs#L6-L35)

## 무엇인가

Uzu는 LLM 이름이 아니라 Mirai의 **Rust 추론엔진**이다. Qwen·LFM 등의 모델을 자체 형식으로 변환해 실행하며, Lalamo는 별도의 변환·최적화 도구다. Rust·Swift·Python·TypeScript 연결과 CPU/Metal backend를 제공한다. 엔진의 MIT와 모델별 라이선스는 구분해야 한다. 예를 들어 공식 Qwen3.5-9B-M 카드는 Apache 2.0을 표시한다. [공식 소개](https://docs.trymirai.com/), [README](https://github.com/trymirai/uzu/tree/0.6.3), [9B 모델 카드](https://huggingface.co/trymirai/Qwen3.5-9B-M/blob/c7be6b81cf077f6b430b332bfad90adf35afa943/README.md)

모델 이름의 **Mirai-M은 4-bit 비대칭 정수 양자화**, Mirai-L은 8-bit 대칭 양자화 계열이다. M/L은 모델 계열 이름이나 M5 칩 종류를 뜻하지 않는다. 9B-M은 group size 32, bf16 scale, 4-bit zero point와 Hadamard 변환을 사용한다. 단순히 '둘 다 4bit'라고 해도 MLX/GGUF와 같은 가중치·품질·파일 크기가 되는 것은 아니다. [공식 양자화 설명](https://trymirai.com/blog/quantization), [9B 형식](https://huggingface.co/trymirai/Qwen3.5-9B-M/blob/c7be6b81cf077f6b430b332bfad90adf35afa943/README.md)

## 숫자의 출처와 조건

### 널리 공유된 base M5 92–117 tok/s

원출처는 Mirai의 공식 벤치마크가 아니라 **Avi Chawla의 2026-10-08 직접 실험 기록**이다. 14인치 MacBook Pro, base M5, 16GB, macOS 26.6.2, Mirai CLI 0.6.1에서 `Qwen3.5-9B-M`과 짧은 Python 함수 프롬프트를 반복했다. Uzu 92–117 tok/s, llama.cpp 약 22, MLX 약 25를 보고한다. Uzu는 DFlash/Weaver 투기적 디코딩을 사용한다. 모델 변환은 Mirai-M / MLX 4bit / GGUF Q4_K_S로 다르며, 비교 MLX·llama.cpp의 정확한 버전은 해당 글에서 확인하지 못했다. [실험 원문](https://blog.dailydoseofds.com/p/karpathys-trick-for-faster-local)

원문의 한 실행은 출력 98.10 tok/s, 첫 토큰 0.12초, prefill 161.11 tok/s, 평균 8.39 tokens/forward pass다. 약 20토큰짜리 프롬프트의 입력 속도는 긴 강의 자료 처리 성능을 대표하지 않는다. 원문에 비교 client와 서버 명령은 있지만, 이번 조사는 이 결과를 재현하지 않았다. 이 단일 코드 과제의 속도를 한국어 요약·JSON 생성·이미지 질의의 평균값으로 사용하지 않는다. [같은 실험의 조건·코드](https://blog.dailydoseofds.com/p/karpathys-trick-for-faster-local)

## 왜 빨라지는가: 입력과 출력을 구분

**Prefill**은 입력을 한꺼번에 처리하는 단계이고, **decode**는 응답을 생성하는 단계다. **TTFT**는 요청 이후 첫 출력 토큰까지 걸린 시간으로, 모델 로딩·서버 대기·전처리·prefill 등 측정 경계에 따라 포함 비용이 다를 수 있다. 입력 tok/s와 출력 tok/s, TTFT를 같은 수치처럼 비교하지 않는다. Apple은 일반적인 prefill을 연산 병목, 단일 순차 decode를 메모리 대역폭 병목으로 설명한다. [Apple의 단계 설명](https://developer.apple.com/videos/play/tech-talks/111432/)

Uzu는 작은 초안 모델이 여러 후속 토큰을 제안하고, 본 모델이 한 번에 검증하는 **투기적 디코딩**을 사용한다. Mirai는 M5를 겨냥해 DFlash-Weaver, 16–32토큰 예산, tree 검증과 int8 활성값 연산을 함께 설계했다고 설명한다. 코드·수학처럼 초안 수락률이 높은 과제에서 이득이 크다는 제작사 주장이다. 모든 모델·프롬프트에서 같은 배수가 보장된다는 뜻은 아니다. [Mirai 구현 발표, 2026-09-03](https://trymirai.com/blog/speculative-decoding-in-uzu)

**M5 GPU의 Neural Accelerator와 ANE(Neural Engine)는 다른 하드웨어다.** Apple은 GPU shader core마다 matrix 연산용 Neural Accelerator가 있고, 별도 16코어 Neural Engine도 있다고 설명한다. MLX·llama.cpp도 GPU Neural Accelerator를 이용할 수 있으므로 Uzu만 접근하는 독점 장치가 아니다. Uzu의 해당 가속은 Metal/GPU 경로에 관한 주장으로 읽어야 한다. Apple의 최대 AI 연산 배수를 그대로 앱의 출력 배수로 환산하지 않는다. [Apple GPU 구조·프레임워크](https://developer.apple.com/videos/play/tech-talks/111432/), [M5 칩 구성](https://www.apple.com/ca/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/)

일반 M5와 Pro/Max도 같지 않다. Apple 사양은 M5 10코어 GPU·153GB/s, Pro 16/20코어 GPU·307GB/s, Max 32/40코어 GPU·460/614GB/s로 구분한다. 공식 성능표의 메모리 용량 표기만으로 정확한 GPU 구성·전력 모드까지 확정하지 않는다. [Apple 기술 사양](https://www.apple.com/uk/macbook-pro/specs/)

## 비교의 공정성과 재현 범위

공식 방법: 입력 약 1,357·출력 최대 4,096토큰, 3회, CPU/GPU 60°C 미만 대기. 출력은 혼합과제·모델권장 sampling이며 미지원시 기본값이다. 입력 분모는 Uzu native / MLX TTFT이고 메모리 counter도 달라 측정 경계가 일치하지 않는다. [방법](https://trymirai.com/metrics)

제작사는 llama.cpp 변환을 KL divergence가 가까운 checkpoint로 고른다고 설명하지만, 같은 모델 이름·4bit가 동일 품질을 보증하지는 않는다. 특히 6월 양자화 글은 Qwen3.5 4B-M의 크기·품질을 Q3_K_M과 Q4_0 사이로 설명한다. 한국어 정확도·출처 인용·schema 충족 품질을 비교하지 않은 상태에서 속도만으로 교체를 결정할 수 없다. [양자화 품질의 범위](https://trymirai.com/blog/quantization)

9월 발표의 specdec 방법은 MT-Bench 80개·MATH-500 128개·HumanEval 128개의 macro-average다. 현행 10월 표의 혼합 데이터셋과 다르다. 양자화 KL 평가에는 private chat 25%가 포함된다. 그 품질 평가를 외부에서 완전히 동일하게 재구성할 수 있다고 주장하지 않는다. [9월 방법](https://trymirai.com/blog/speculative-decoding-in-uzu)

공개 Uzu CLI에는 `bench MODEL_PATH TASK_PATH OUTPUT_PATH`와 task/result 타입, warm-up·reset·반복 실행 구현이 있다. 결과에 OS·CPU·RAM·엔진 버전·timestamp·입출력 토큰·TTFT·속도를 남길 수 있다. 반면 확인한 공식 성능표에는 개별 실행 원자료, 모든 prompt의 정확한 토큰열, context 설정, macOS, GPU 코어 구성, 전력 모드, seed, 전체 비교 harness의 고정 commit이 충분히 드러나 있지 않다. **재현 기능의 공개와 공식 숫자의 독립 재현 완료는 다르다.** 이번 조사에서 독립 기관의 공식 검증은 확인하지 못했고 직접 재현도 하지 않았다. [CLI 명령](https://github.com/trymirai/uzu/tree/0.6.3#benchmarks), [task/result 타입](https://github.com/trymirai/uzu/blob/0.6.3/crates/legacy/cli/src/bench/model.rs), [warm-up과 반복](https://github.com/trymirai/uzu/blob/0.6.3/crates/legacy/cli/src/bench/runner.rs#L69-L85)

공식 비교에 Ollama는 없다. MLX 수치를 앱의 **Ollama v0.40.3 / MLX·vision·grammar·전사 병행** 결과로 사용할 수 없다. [참가자](https://trymirai.com/metrics), [앱 계약](2026-10-14-ollama-provider-contract.md)

## M4에서도 같은 이득이 있는가

공식 Qwen3.5-9B-M의 고정 revision `c7be6b81cf077f6b430b332bfad90adf35afa943`의 `speculator/shapes.json`에는 M5·M5 Pro·M5 Max와 M6만 있으며 M4와 `default`는 없다. 0.6.3 loader는 현재 장치 이름 또는 `default`에 맞는 shape가 없으면 `Ok(None)`을 반환한다. **이 checkpoint의 기본 구성에서는 M4가 해당 투기적 디코딩 경로를 받지 않는다는 소스 근거**다. Uzu 엔진의 모든 미래 모델이 M4에서 투기적 디코딩을 영원히 지원하지 않는다는 뜻은 아니다. [공식 모델 shapes](https://huggingface.co/trymirai/Qwen3.5-9B-M/blob/c7be6b81cf077f6b430b332bfad90adf35afa943/speculator/shapes.json), [0.6.3 선택 코드](https://github.com/trymirai/uzu/blob/0.6.3/crates/uzu-engine/src/speculators/dflash_tfm.rs#L98-L113)

현재 4B/M4에서 교체를 서두를 정도의 출력 개선은 위 표에서 보이지 않는다. 32GB 공식 장치를 16GiB 사용자 PC의 RAM·swap·동시 실행 적합성 근거로 사용하지 않는다. M5를 구매해야 한다거나 9B가 이 앱에서 더 낫다는 결론도 이 조사에서 나오지 않는다.

## 추후 채택을 판단할 최소 확인 목록 — 이번에는 실행하지 않음

1. 실제 M4 / 16GiB에서 현재 Ollama/Qwen4B와 Uzu의 같은 원본 모델·revision, 가능한 가까운 양자화 품질, 같은 템플릿·thinking·sampling·입출력 길이를 기록한다. 형태가 다른 checkpoint는 그 차이를 남긴다.
2. 첫 실행과 warm 실행, prefix cache 유무, AR와 specdec를 나누고 TTFT·prefill·decode·전체 완료 시간·RAM/swap을 측정한다. 전사 단독과 전사+생성도 구분한다.
3. 실제 한국어 강의 요청으로 요약 정확성·근거 인용·schema 충족률을 함께 확인한다. 짧은 코드 생성 속도를 합격 기준으로 삼지 않는다.
4. enum·anyOf·배열 개수 조건, 잘린 JSON, 취소 중단·재요청, 모델 식별 실패를 확인한다. vision·embedding 지원이 확보되지 않으면 그 경로를 포함한 전체 교체로 표현하지 않는다.
5. 전용 모델의 신규 저장 비용·라이선스 고지·OS·패키징·업데이트·정리 계약을 검토한 뒤 채택 범위를 결정한다.

이 문서는 공개 근거를 정리한 결과다. Uzu의 로컬 성능, 앱 통합 성공, 한국어 품질, 사용자 M4의 메모리 적합성은 검증하지 않았다.
