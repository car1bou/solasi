# Mac 펜·형광펜 원본 재연결 검증

2026-11-05, 실제 설치된 Solasi **0.3.39 / build 49**. 창은 **680×480**, 캡처는 **1360×960**이다. 기존 검증 과목의 별도 PDF를 사용했다. 이 검증으로 앱 실행 코드나 엔진을 변경하지 않았다.

## 드래그 대상 창 진단

접근성 목록에는 Solasi의 일반 창·HTML·필기 도구가 보이고 스크린샷도 반환됐지만, 좌표 입력은 이전 검증에서 `noWindowsAvailable`로 실패했다. 앱을 획득했다는 사실을 좌표 입력 가능한 활성 창이 준비됐다는 증거로 사용하면 안 된다. 도구의 앱 획득 API는 앱을 배경에서 실행할 수 있다.

이번에는 **앱 재획득 → Solasi 메뉴 → Solasi 열기**를 실행한 뒤 동일한 화면 좌표의 펜 드래그가 전달되고 저장되는 것을 확인했다. `Solasi 열기`는 기존 `showWindow()`의 최소화 해제·`makeKeyAndOrderFront`·`NSApp.activate` 경로다. 이후 형광펜 드래그도 정상 전달됐다. 재실행 후에도 같은 창 활성화 경로로 HTML을 다시 확인했다. 앱 창 코드는 바꾸지 않았다.

확인한 경계는 **앱/접근성 대상의 존재와 좌표 입력·캡처용 창 준비 상태의 차이**다. 창이 아예 없는 앱이나 필기 저장 오류로 볼 근거는 없었다. 별도로 ScreenCaptureKit `-3811/-3812` 캡처 오류도 관측됐다. 이 SDK 내부 오류의 정확한 원인을 입증하거나 영구 해결한 것은 아니다. 실패 후 창을 다시 획득하고 실제 저장 상태를 확인한 다음 계속했다.

### 재사용할 검증 절차

1. 실행 중인 앱 객체를 다시 획득하고 접근성 목록·스크린샷을 확인한다.
2. 메뉴의 **Solasi → Solasi 열기**로 창을 명시적으로 활성화한다. 작은 창은 **윈도우 → 작은 창 (680×480)**을 사용한다.
3. 도구를 선택하고 새 접근성 상태에서 선택 여부를 확인한다. 직후 스냅샷이 이전 상태를 반환한 사례가 있어 스크린샷과 저장 상태를 별도로 대조한다.
4. 현재 스크린샷의 종이 안 좌표로 한 번만 드래그한다. 이번 펜은 `(730,600) → (1150,640)`, 형광펜은 `(510,510) → (1160,510)`에서 입력됐다. 이 좌표는 당시 캡처에만 유효하다.
5. 오류가 나도 즉시 같은 획을 반복하지 않는다. 페이지 revision·ink와 화면을 먼저 확인해 입력 실패와 후속 캡처 실패를 구분한다.
6. 기본 선택창·페이지 재진입 뒤에도 새 화면을 확인하고 다음 조작을 진행한다. 테마 변경은 최종 화면 값과 저장 결과까지 확인한다.

## 실제 필기·복구 결과

| 단계 | 결과 |
| --- | --- |
| 펜 입력 | 마우스 드래그로 녹색 사선 획을 입력, v3 저장 |
| 형광펜 입력 | 같은 페이지 본문 위에 반투명 획을 입력, v4 저장 |
| 저장 기준 | 메모와 pen·highlighter 두 획의 전체 좌표·색·굵기·불투명도·입력 속성을 별도 기준으로 보존 |
| 라이트·다크 | 두 모드의680×480에서 원본과 두 획 표시 확인. PDF 원본과 필기 색은 동일하게 유지 |
| 원본 이동 | 검증 PDF만 다른 폴더로 이동. 파일 없음 표시와 v4 보존 확인 |
| 원본 다시 찾기 | 실제 네이티브 선택창에서 이동한 동일 파일 선택. 기존 자료 ID·문서 SHA256·추출 버전 보존 |
| 재연결 뒤 | 페이지 ID·revision·메모·ink 문자열 전체가 저장 기준과 정확히 일치 |
| 정상 종료·재실행 | 정상 종료 뒤와 재실행 뒤 각각 같은 v4·두 획·메모 확인 |
| 재실행한 라이트·다크 | 원본 페이지 위에 같은 두 획 표시 확인. 저장 기준과 전체 데이터 일치 |

ink 문자열 SHA256은 저장·재연결·정상 종료·재실행·다크 복원 단계 모두 `a8a8683da9aa84c3a0f5d98f9169f0b56a4fb15736b130ffbe30b7b8ab0f130c`로 일치했다. 마우스로 만든 두 직선 획이며 각 획은 두 점으로 저장됐다. 곡선·필압 펜 하드웨어를 검사했다고 해석하지 않는다.

## 보존 대조

검증 시작 전에 실행 중 보관함의 일관된 SQLite 백업과 보관함 내 파일 해시 목록을 만들었다. 검사 범위는 기록·출처·필기 관련 12개 테이블의 기존 행이며, 자동 처리로 추가되는 색인·작업 큐 전체의 정지를 의미하지 않는다. 검사한 기존 4,181개 행 중 **4,177개 행은 그대로**다. 바뀐 네 행은 아래 검증 자료의 예상 변경뿐이며 필드 수준으로 제한해 대조했다.

- 검증 페이지의 현재 revision: v2 → v4. 기존 v1·v2와 새 v3·v4 기록은 유지.
- 해당 페이지의 저장 초안 값.
- 필기 변경으로 무효화된 해당 페이지의 이전 인식 후보 상태: `stale`. 인식문을 새 지식으로 자동 승인하지 않음.
- 해당 검증 PDF의 외부 원본 경로.

보관함 내 기존 파일 **73개**(페이지 PNG 50개·추출 JSON 14개·녹음 WAV 9개)의 크기·SHA256은 전부 같았다. 이 목록은 외부 연결 원본 전체의 목록이 아니다. 이동한 검증 PDF의 원본 SHA256은 재연결·재실행 단계에서 별도로 대조했다. 기존 도구·과목 목록·테마 설정을 복원했고 앱 서명 검사도 통과했다. 최종 앱은 다크 모드의 검증 PDF 화면으로 남겼다. 이동한 검증 PDF는 새 위치에 연결된 채 보관한다.

## 범위와 한계

실제 재연결과 재실행에서 필기 유실을 재현하지 못해 제품 코드·데이터 구조·앱 버전은 변경하지 않았다. 이번 변경은 검증 절차와 증거 기록이다. 이전 메모 중심 검증의 미확인 범위를 이번 두 획 검증으로 보완한다.

새 ASR·생성 모델 시험, 장시간 녹음, 실제 스타일러스 필압, 강제 종료·절전은 이번에 재실행하지 않았다. SDK 캡처 오류가 다시 발생할 가능성은 남으며 위 절차는 이를 영구 수정했다는 주장이 아니다. 보관함·필기 원본 JSON·캡처·백업은 공개 Git에 포함하지 않는다.
