# Mac 앱 내부 실행 전환 설계

날짜: 2026-10-16 (Asia/Seoul)

상태: 사용자가 상세 설계에 따라 구현 계획을 작성하고 진행하도록 승인했다. 기존 모델의 직접 실행 호환성을 먼저 확인하며, 현재 앱 교체는 데이터·초안 이전과 별도 앱 검증 이후에 수행한다.

## 1. 목적과 확정 범위

사용자는 서버를 따로 돌리는 구조를 앱 내부 실행으로 바꾸기를 원한다. Mac을 먼저 완성하며 현재 화면, 과목·회의 기록, 원음, 전사 수정 이력, PDF 페이지 메모·필기, API 선택 기능을 이어서 사용한다.

- Solasi 기본 실행은 HTTP/WebSocket 서버, Ollama 서버, 로컬 TCP/UDP 리스너를 시작하지 않는다.
- 앱 화면·처리 코드·필수 런타임을 앱 패키지에 포함한다. 개발 checkout, 별도 Python·Node 설치와 실행 중 빌드가 사용자 실행의 전제여서는 안 된다.
- 모델·사용자 보관함은 쓰기 가능한 앱 관리 위치 또는 기존 보관함에 둔다. 서명된 앱 번들에 사용자 기록이나 다운로드 모델을 쓰지 않는다.
- 무거운 추론은 앱이 소유한 작업 프로세스로 분리한다. 앱 내부 실행을 모든 추론을 UI 프로세스에서 실행한다는 뜻으로 해석하지 않는다.
- 외부 AI API·웹 검색은 기존 사용자 선택에 따른 외부 연결이다. 로컬 실행 전환 때문에 업로드나 API 사용을 자동으로 켜지 않는다.
- 녹음 종료 후 전사 기본값, 선택적 실시간 전사, 전사 우선순위, 재전사 후보의 사용자 적용, 로컬 핵심 원문 발췌 요약 정책을 유지한다.

서버 제거의 직접 목적은 포트 충돌·서버 준비 연결·개발 환경 의존을 줄이는 것이다. 모델 추론 속도와 메모리 절약은 달성 여부를 별도로 측정한다. 현재 UI도 WKWebView이므로 이 전환만으로 화면 엔진의 메모리가 없어지지는 않는다.

## 2. 현재 코드에서 확인한 사실

- `macos/Solasi.swift`는 AppKit 창과 WKWebView를 만들고, `launch.json`의 외부 Python·소스 경로로 launcher를 실행한다. stdout의 실행 링크와 HTTP health 확인 뒤 화면을 연다.
- `scripts/install_macos_app.py`의 현재 앱은 실행 파일·아이콘·설정만 포함한다. Python·화면 자산·프로젝트 모듈은 외부 경로를 사용한다.
- `lecture_study/launcher.py`가 loopback TCP socket과 Uvicorn 서버를 시작한다. 관리형 `OwnedOllama`는 별도의 loopback 포트를 연다.
- JSON 요청은 `frontend/src/api.ts`에 모였지만, PDF·이미지·음성·내보내기 링크는 별도 URL을 사용한다. 녹음은 getUserMedia·AudioWorklet·WebSocket과 PCM 저장 ACK에 의존한다.
- 페이지 초안·다른 창의 미저장 journal은 IndexedDB, 화면 모드는 localStorage에 있다. 새 앱 origin에서 기존 초안이 자동으로 보인다고 가정할 수 없다.
- 기존 검사에는 소켓 없이 동일 ASGI HTTP·WebSocket 핸들러를 호출하는 사례가 있다. 도메인 로직 전체를 새 언어로 옮길 필요는 없다.

읽기 전용 조사로 확인한 현재 모델:

| 자산 | 확인한 형식 | 실행 호환성 상태 |
| --- | --- | --- |
| Qwen3.5 4B | Ollama tensor blob 723개와 config·tokenizer 등. 개별 safetensors, NVFP4 group16 | 표준 MLX 폴더 배치가 아니며 직접 로딩 미검증 |
| Gemma4 12B | tensor blob 725개와 JSON 등. mixed precision/NVFP4 및 draft 구성 | 직접 로딩·구조화 출력·vision 미검증 |
| EmbeddingGemma | 단일 GGUF v3 BF16, 모델 본체 약 622MB | 파일 재사용 후보. 설치된 libllama는 x86_64로 M4 arm64에 직접 로드할 수 없음 |
| Whisper·Qwen ASR | 현재 CLI 또는 별도 작업 프로세스 경로 | 기존 자산 재사용을 우선하되 패키징 뒤 다시 실행 확인 |

주 Python 환경에는 mlx-lm·mlx-vlm이 설치돼 있지 않다. 별도 ASR 비교 환경의 mlx-audio 또는 Ollama의 MLX dylib가 생성·vision·임베딩 호환성을 제공한다고 간주하지 않는다.

## 3. 선택한 구조와 대안

| 방식 | 변경 범위 | 판단 |
| --- | --- | --- |
| **기존 화면·Python 처리 재사용, 네이티브 기능과 내부 IPC 연결** | 화면 자산, 통신, 녹음, 모델 provider, 앱 패키징을 변경 | 추천. 저장·검색·요약·검증 로직 재사용 가능 |
| UI·저장·검색·AI 제어를 Swift 중심으로 재작성 | 화면과 도메인 로직 전반 이식 | 큰 회귀 범위와 다른 OS 확장 비용이 있어 이번 전환에서 선택하지 않음 |

```text
Solasi.app
  ├─ 기존 React 화면: 앱 번들의 자산을 WKWebView에 표시
  ├─ Swift: 창·권한·마이크·파일 선택·내보내기·제한된 자산 접근
  └─ 내부 파이프 통신
       └─ 앱 작업 엔진: 기존 검증·SQLite·검색·작업·요약 로직
            ├─ Whisper / Qwen ASR 작업 프로세스
            ├─ 직접 실행하는 로컬 생성·이미지 모델
            └─ 직접 실행하는 임베딩 엔진
```

### 3.1 내부 명령과 작업 수명

- Swift와 작업 엔진은 상속받은 stdin/stdout 파이프로 통신한다. Unix socket이나 네트워크 리스너를 새로 만들지 않는다.
- 프로토콜은 버전, 요청 ID, 고정된 동작 종류, 크기가 검증된 JSON·바이너리 프레임으로 구성한다. stderr는 로그 전용이며 stdout에 모델 로그나 임의 텍스트를 섞지 않는다.
- 첫 전환에서는 기존 FastAPI 앱을 한 번 만들고 ASGI 요청·응답을 파이프로 전달해 라우팅·입력 모델·409/422 오류·작업 제어를 재사용한다. Uvicorn과 socket bind는 실행하지 않는다.
- 앱 전체 실행 동안 event loop·DB·단일 데이터 폴더 락·lifespan을 하나 유지한다. 요청마다 앱을 만들거나 동기 pipe 읽기로 event loop를 막지 않는다.
- 기존 작업 조회·취소·대기 흐름을 재사용한다. 이번 전환에 토큰 스트리밍이나 새로운 자동 재시도 정책을 추가하지 않는다.
- EOF·정상 종료·소유 앱 소실·worker 오류는 작업 취소, 원음 마무리, 자식 추론 회수, DB/락 정리로 연결한다. 재실행 시 기존 중단 작업 복구 경로를 유지한다.
- UI는 앱 번들의 신뢰한 main frame만 브리지를 호출한다. 임의 명령 실행·임의 Python import·임의 경로 읽기 기능을 노출하지 않는다. 내부 ASGI 인증 정보는 JS 입력으로 받지 않는다.

### 3.2 녹음

- Mac의 마이크 수집을 네이티브 AVAudioEngine으로 옮긴다. 현재 브라우저 getUserMedia·AudioWorklet·WebSocket은 Mac 기본 녹음 경로에서 제거한다.
- 실시간 오디오 callback에서 디스크·DB 쓰기나 모델 실행을 하지 않는다. 별도 직렬 큐에서 mono s16 PCM packet을 만들고 내부 바이너리 채널로 저장 엔진에 전달한다.
- 기존 seq·first_frame·frame_count, 중복 packet의 내용 대조, 제한된 전송 대기 버퍼, 디스크 반영·DB commit 뒤 ACK 원칙을 유지한다. pipe 쓰기 완료를 저장 완료로 표시하지 않는다.
- 하드웨어 sample rate와 실제 입력 시각을 기준으로 기록한다. 입력 간격을 LLM 추정이나 글자 수로 메우지 않는다.
- 기존 30초 마이크 연결 대기 제한과 늦은 응답 무효화, 정상 무음 보존, 살아 있는 마이크의 실제 입력 복귀 후 한 번만 새 구간을 여는 정책을 적용한다.
- 잠자기·깨우기·입력 장치 변경 시 같은 원음을 조용히 이어 붙이지 않는다. 이전 저장 원음과 간격을 보존하고 복구 실패 시 수동 재시작을 표시한다.

### 3.3 PDF·음성·파일과 내보내기

- 화면 자산·제한된 자료 URL은 앱 전용 scheme handler로 연결한다. 자료·녹음 ID와 버전을 기존 파일 검증 함수로 해석한다. 파일 소속·삭제 상태·원본 해시 검증을 우회하지 않는다.
- 긴 WAV·PDF를 JSON/base64 전체 응답으로 모으지 않는다. bounded chunk, 취소, HEAD·Range·부분 응답을 지원한다. 설치된 HTTPX ASGITransport의 전체 body buffering을 긴 파일 전달에 사용하지 않는다.
- 선택 구간 재생·seek·원본 새 창은 실제 WKWebView 자산 경로로 검사한다. 미디어에서 요구되는 Range 동작을 충족하지 못하면 앱의 네이티브 미디어 재생 경로로 처리하며, 미검증 상태에서 화면만 연결됐다고 완료하지 않는다.
- 파일 선택은 주 앱의 NSOpenPanel로 통합한다. 새 외부 FilePicker 앱의 실행 중 빌드 의존을 제거한다.
- NSSavePanel, 기존 파일 보존, 임시 파일·exclusive rename, 취소·실패 정리를 TXT·Markdown·JSON 내보내기에 적용한다.
- 새 Markdown 원음 링크는 읽기·재생용 앱 링크로 만든다. 링크로 녹음 시작·삭제·API 요청 같은 변경 작업을 실행하지 않는다. 해당 로컬 보관함과 원음이 있어야 열린다.
- 이미 앱 밖에 내보낸 Markdown의 과거 `http://127.0.0.1:포트` 링크를 리스너 없이 그대로 제공할 수는 없다. 원래 문서는 자동 수정하지 않고 새 링크를 쓰는 문서로 다시 내보낸다. 기존 SQLite 근거·전사 ID와 원문은 보존한다.

## 4. 모델 직접 실행과 호환성 관문

### 4.1 구현 전에 실행으로 판별할 사항

첫 실행 단계는 설치 모델의 작은 직접 추론 비교다. 제품 앱 교체 전에 다음을 확인한다.

1. Qwen3.5 4B의 기존 NVFP4 tensor·tokenizer·config를 읽기 전용으로 재사용해 직접 MLX 실행이 가능한지 확인한다. 필요한 파일 배치는 중복 가중치 복사 없이 구성하고 원래 blob·manifest를 바꾸지 않는다.
2. 텍스트·이미지·구조화 JSON·출력 제한·취소·tokenizer 입력 예산을 기존 앱 계약으로 검사한다. safetensors 파일이라는 이유만으로 통과시키지 않는다.
3. EmbeddingGemma GGUF를 직접 실행할 arm64 llama.cpp 엔진을 준비하고 prefix·pooling·정규화·차원·빈 입력·입력 한도를 확인한다. 현재 x86_64 dylib를 arm64 Python에 로드하지 않는다.
4. Gemma4 등 다른 설치 모델은 모델별로 직접 실행과 기능을 확인한다. 하나의 모델 성공으로 나머지를 준비 완료로 표시하지 않는다.

MLX는 Mac 생성·vision 경로의 우선 후보, llama.cpp는 기존 GGUF 임베딩 자산을 직접 실행할 후보다. **현재 파일의 직접 실행 성공은 아직 확인되지 않았다.** 호환 관문을 통과한 라이브러리 revision·바이너리·기능·파일 해시를 고정해 구현 계획에 반영한다. 호환 실패 시 실제 실패를 기록하고 현재 앱을 보존한다. 새 대형 모델이나 별도 변환 사본이 필요하면 용량·조건·저장 공간을 제시해 기존 다운로드 동의 규칙을 따른다.

### 4.2 앱 통합 계약

- 런타임의 앱 소유 Ollama 시작·조회·다운로드·chat·embed 호출을 직접 모델 관리와 실행으로 교체한다. 내부에서 llama-server·mlx server를 다시 띄우는 방법은 사용하지 않는다.
- provider 이름을 기준으로 하던 전사 우선순위, 생성 동시 실행 제한, 임베딩 대기, 질문 후보 자동 실행 제한을 새 로컬 provider에도 적용한다. API 제공자를 로컬 모델로 오인하지 않는다.
- 모델 가중치·tokenizer·chat template·런타임 식별을 새 요청의 근거에 기록한다. 이전 Ollama 결과와 모델 metadata는 과거 기록으로 보존한다.
- 과거 미완료 작업의 실행 엔진·입력 예산·요청 계약이 달라졌으면 조용히 다른 모델로 이어 실행하지 않는다. 완료 부분을 열 수 있게 보존하고 새 요청으로 재시도하도록 표시한다.
- 기존 임베딩과 새 엔진의 query vector를 호환 검증 없이 혼합하지 않는다. 엔진·template·pooling·차원을 포함한 새 색인을 준비하고 완료한 뒤 전환한다. 준비 전에는 키워드 검색과 기존 기록 조회를 제공한다.
- 모델은 요청 시 로드하고 한 번에 필요한 모델만 유지한다. 전사·생성·임베딩이 경쟁할 때 기존 전사 우선 정책을 적용한다. warm 유지·해제는 실제 RAM·지연 결과로 판단한다.

## 5. 기록·초안 이전과 패키징

- SQLite의 기존 ID·원음 상대 연결·자료 원본 연결·노트 및 필기 버전·완료 생성 결과를 보존한다. 전환을 위해 원본 PDF·오디오를 새로 업로드하거나 전부 복사하지 않는다.
- 기존 보관함과 모델 위치를 우선 재사용한다. 이번 통신 전환에 기존 사용자 파일의 대규모 폴더 이동·자동 삭제를 끼워 넣지 않는다. 새 설치의 기본 보관함은 Application Support 아래에 둔다.
- 기존 HTTP origin을 사용하는 마지막 이전 단계에서 모든 페이지 초안·다른 창 journal·복구 사본·화면 모드를 내보내 별도 로컬 이전 파일로 저장한다. 새 저장소에 import하고 내용·개수·버전 대조 및 재시작 복구가 끝나기 전 이전 저장소를 정리하지 않는다.
- 이전 단계는 기존 앱의 현재 origin에서 수행한다. 새 앱 기본 실행이 옛 HTTP origin을 재현하려고 서버를 계속 띄우는 방식은 사용하지 않는다. 이전 파일이 검증되지 않으면 기존 앱을 새 앱으로 교체하지 않는다.
- 앱 내부 초안 저장은 보관함별로 분리하고, origin 변경에만 의존하지 않는 앱 저장 경계로 연결한다. 저장 완료 전에는 완료 표시를 하지 않는다. 현재 페이지 conflict·expected revision·백업 선택 동작을 유지한다.
- Python 처리 엔진은 onedir 형태로 freeze해 실행 코드·Python·필수 extension·라이브러리·자료를 앱에 포함하는 방식을 우선한다. 모델 작업별 진입점도 패키징에 포함하며, frozen executable에 개발 환경의 `python -m` 실행을 요구하지 않는다.
- 엔진 자산·MLX/Metal library·토크나이저 파일·OCR/추출 의존성을 목록화해 앱 포함 또는 기존 사용자 엔진 자산 재사용을 명시한다. 앱 실행 시 npm·pip·컴파일러를 호출하지 않는다.
- 빌드는 임시 영역에 준비하고 필요한 실제 추가 용량을 확인한다. 모델 중복 복사나 여러 전체 앱 백업을 무제한 생성하지 않는다. 현재 사용 중인 모델·사용자 데이터·검증 기록을 용량 확보 목적으로 자동 삭제하지 않는다.
- 기존 앱은 새 앱의 별도 보관함 검증과 이전 검증이 끝난 뒤 교체한다. 실패하면 이전 앱·이전 파일을 보존해 돌아갈 수 있어야 한다. Apple 서명·권한 요청은 실제 시스템 결과로 확인하며, ad-hoc 서명만으로 공증 배포판이라고 표시하지 않는다.

## 6. 변경이 도달해야 할 곳

| 영역 | 변경·검사 대상 |
| --- | --- |
| Mac shell | 실행 설정·worker 수명·브리지 신뢰·마이크·파일 선택·저장·새 창·앱 링크·로그 |
| 처리 엔진 | ASGI/IPC adapter·lifespan·취소·부모 소실·PCM·긴 자산의 streaming |
| 프런트엔드 | api.ts·recording-capture·모델 설정·파일/원음 URL·내보내기·초안 저장 경계 |
| 모델/검색 | local_models·providers·retrieval·token_budget·로컬 판단 및 SQL 조건·설치 catalog |
| 기록 호환 | 이전 요청 snapshot·과거 provider metadata·근거 링크·임베딩 색인·미저장 초안 |
| 배포/검증 | installer·앱 번들 엔진·라이선스/해시 목록·native fixture·문서·소스 실행 보조 경로 |

기존 소스 실행 CLI를 다른 개발·검증 용도로 남기더라도, 이를 새 앱의 실패 fallback으로 자동 실행하지 않는다. 앱에서 서버로 되돌아가면 완료 조건을 충족하지 않는다.

## 7. 전환 완료를 확인할 방법

아래는 수행할 검사이며 현재 통과한 결과가 아니다.

1. 과목 생성 → 자료 연결 → 페이지 메모·필기 → 녹음 → 전사 → 선택 재생·수정 → 요약·검색 → 내보내기를 앱에서 실행한다.
2. 앱과 소유 자식의 listener를 확인해 Python·Ollama·다른 모델용 TCP/UDP 리스너가 없음을 증명한다. 외부 API·다운로드의 outbound 연결과 listener를 구분한다.
3. 기존 포트가 다른 프로세스에 점유돼 있어도 새 앱이 기동한다. 개발 소스·외부 Python을 참조하지 않는 패키지 실행을 확인한다.
4. 원본·원음 Range/seek·잘못된 ID·소속 위반·파일 변경·삭제·과대 본문·브리지 외부 frame 요청을 검사한다. 긴 원음을 통째로 메모리에 모으지 않는지 확인한다.
5. 기존 실제 음성으로 전사·생성·필기 동시 실행, 마이크 최초 허용·취소·시간 초과, 장시간 저장·실제 절전·복귀·강제 종료·재실행을 확인한다. 모의 입력과 실제 마이크 결과를 구분한다.
6. 이전된 미저장 초안·여러 창 사본, 저장 실패 중 메모·완료 획, v1 이전 기록·원음 해시를 대조한다. 교체 실패 때 기존 앱을 유지하는지 확인한다.
7. 같은 모델·양자화·입력·출력 제한·실행 순서를 맞춰 시작 시간, idle RAM, peak RAM, 전사 완료 시간, 생성 시작/완료 시간, 구조화 출력·의미 검색·vision 품질을 비교한다. 엔진 변경을 서버 통신 비용 차이로 해석하지 않는다.
8. 모델 호환 관문을 통과하지 못했거나 기존 핵심 기능이 빠졌으면 완전 내장 전환 완료로 표시하지 않는다.

## 8. 검토 후 진행 순서

이 설계 승인 뒤 구현 계획을 작성한다. 첫 실행 단계는 모델 직접 실행·미디어 자산·초안 이전의 위험을 작은 검증으로 판별하고, 이후 내부 worker와 네이티브 녹음, 패키징과 전체 흐름을 이어 구현한다. Windows·Android·iPadOS의 런타임·녹음·패키징은 Mac 검증 이후 별도 설계한다.
