# 필기 이미지 생성·인식 엔진 분리

2026-10-27 · 사용자 승인 · 구현·검증 완료

## 목적과 범위

사용자가 요청한 것은 기존 Mac의 필기·인식·승인·검색을 보존하면서 다른 OS의 이미지 생성기와 인식 엔진을 연결할 수 있도록 경계를 분리하는 것이다. 이번에는 Windows·Android 앱이나 새 OCR 모델을 구현·배포하지 않는다. 각 기기 로컬 저장·처리 원칙을 유지한다.

변경 전 `recognize_ink`는 Swift helper에서 이미지 생성과 Vision OCR을 함께 실행했다. Qwen·Gemma도 이 함수를 PNG 생성용으로 호출하므로 Vision에 의존했다. 승인·검색·필기 버전 관리는 이 결합과 별개이며 유지했다.

## 접근 방식

1. **현재 Mac 렌더러를 유지하고 호출 단계를 분리 — 추천.** 기존 CoreGraphics/PDFKit의 획 모양·압력·좌표·페이지 합성을 보존한다. 공통 처리는 PNG와 인식 결과를 주고받으며, 다른 OS 구현은 이 접점에 연결한다.
2. Python 공통 렌더러로 즉시 교체. 다른 데스크톱에서 실행할 여지는 있지만 획·안티앨리어싱·PDF 페이지가 달라질 수 있고, 모바일 이식까지 해결하지 않는다. 기존 Mac 동작 보존이라는 이번 범위에 비해 변경이 크다.

사용자가 선택한 이미지 생성·인식 분리 방향을 구체화한 문서다. 사용자는 1번의 네이티브 렌더링 유지와 아래 모듈 경계를 승인했다.

## 처리 경계

공통 흐름은 다음과 같다.

`저장된 필기 스냅샷 → 검증된 렌더링 입력 → PNG → 선택한 인식 엔진 → 기존 후보 저장 → 사용자 승인 → 기존 색인·검색`

- 이미지 생성기는 검증된 pen 획·페이지 크기·선택적 원본 페이지를 받아 지정된 임시 PNG를 생성한다. OCR이나 언어 지원 검사를 수행하지 않는다.
- 이미지 인식 엔진은 생성된 이미지 파일을 받아 기존 `engine / regions` 결과를 반환한다. 이미지 생성기나 Apple Vision을 임의로 호출하지 않는다.
- Python의 공통 조합 함수는 이미지 생성과 인식 호출을 연결한다. 기존 서버 진입점 `recognize_ink`와 `recognize_local_ink`의 기존 호출을 유지하고, 다른 OS 구현을 주입할 수 있는 접점을 제공한다. 엔진 등록 시스템이나 새 사용자 설정은 추가하지 않는다.
- Mac의 helper 실행·플랫폼 검사·Swift CLI 인수는 Mac 전용 adapter로 모은다. 다른 OS용 생성기·엔진을 지정한 공통 흐름에는 Mac 검사와 Swift 실행이 개입하지 않는다.
- Qwen·Gemma에 이미지를 전달하는 부분도 이미지 입력 함수로 분리한다. 현재 MLX manager의 다른 OS 실행까지 제공하거나 검증했다고 주장하지 않는다.

## Mac 호환 계약

- 기존 Swift 렌더러와 `HandwritingRecognition` 빌드 산출물 이름을 유지한다. helper에 OCR을 하지 않는 `--render-only`를 추가하고, 기존 결합 모드와 `--recognize-image`는 호환용으로 보존한다.
- 흰 배경·검정 pen·최대 2400px·최대 3배·압력 굵기·round cap/join·highlighter 제외·top-left 정규화 좌표·PDF cropBox·실제 파일 형식 판별을 유지한다.
- Vision accurate·언어 교정 끔·한국어/영어·bbox clipping·후보 점수·revision·languages·`edge_touching`을 유지한다.
- `engine` 문자열과 원본 페이지의 `/page` 접미사를 보존한다. 접미사는 `second_brain.reconcile`의 중복 자동 인식 방지에 쓰이므로 표시 문자열로 취급해 변경하지 않는다.
- Qwen·Gemma의 원본 사진 선택·EXIF 보정·Qwen 1회 확대·큰 사진/PDF의 bounded render·프롬프트·모델 digest·출력 상한·실제 ink bbox를 유지한다.
- Mac의 Qwen·Gemma에는 기존 Vision 기반 잘림 경고를 **별도의 진단 단계**로 유지한다. 렌더링이나 로컬 모델 엔진 자체가 Vision을 요구하지 않도록 분리한다. 다른 OS의 진단은 교체하거나 생략할 수 있고, 진단하지 않은 상태를 '잘림 없음'으로 확정하지 않는다. 현재 Mac 진단 실패 시 처리 정책은 바꾸지 않는다.

## 데이터와 오류 처리

DB 스키마·획 형식·기존 인식 레코드·승인 출처·검색 조건·자동 작업 키를 바꾸지 않는다. 기존 완료 후보나 사용자 수정문을 재작성·재인식하지 않는다. 필기 변경 시 stale·현재 검색 제외와 과거 출처 보존을 유지한다.

임시 이미지는 요청이 소유한 폴더에서 처리하고, 성공·실패·취소 시 정리한다. 기존 입력 크기·좌표·PNG 크기 검사와 자식 프로세스 종료를 보존한다. 준비되지 않은 OS 엔진을 조용히 다른 모델이나 외부 API로 전환하지 않는다.

## 변경 대상과 검증

- `lecture_study/handwriting.py`: 조합 함수와 기존 승인·저장 경계 유지, 이미지 입력 로컬 인식 분리.
- 새 Mac adapter 모듈: helper 실행, 이미지 생성, Vision 이미지 인식의 별도 함수. 함수·입출력 경계만 추가하고 범용 플러그인 시스템은 만들지 않는다.
- `macos/HandwritingRecognition.swift`: render-only 경로. 빌드 스크립트의 helper 이름·기존 CLI를 유지한다.
- 관련 테스트·개발 문서: 새 접점, 실제 Mac 검증, 다른 OS 연결 예제와 미구현 범위.

구현 전 기존 helper를 별도 검증 폴더에 빌드해 기준을 보존한다. 같은 획·사진·PDF에서 분리 전후 PNG의 크기와 픽셀, 실제 Vision의 문장·bbox·메타데이터를 대조한다. Qwen·Gemma에는 동일한 최종 이미지가 들어가는지 확인하고 설치된 모델로 실제 인식도 비교한다. 새 모델 다운로드는 하지 않는다.

Mac 전용 함수를 사용할 수 없는 조건에서도 대체 생성기·인식기를 연결한 공통 흐름을 검사한다. 승인 전 검색 차단, 수정·승인 후 색인, 필기 변경·삭제 후 현재 검색 제외, 과거 출처와 미승인 초안 복구, `/page` 자동 작업 중복 방지를 회귀 검사한다.

격리된 검증 보관함과 Mac 실행 경로에서 실제 흐름을 확인한다. 현재 사용자 보관함은 검증 데이터로 수정하지 않는다. 실제 설치 앱 교체가 필요하면 미저장 작업을 확인한 뒤 진행한다. 전체 회귀 검사·프런트엔드 검사·Mac helper 빌드·독립 검토를 마친 후 정확한 변경 파일만 커밋·main에 푸시하고 원격 SHA를 확인한다.
